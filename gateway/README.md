# Gateway (Raspberry Pi)

Der Ordner enthält alles, was auf einem Gateway läuft: Mosquitto (lokaler Broker mit Bridge zum Plattform-Broker, ADR-0020) und Zigbee2MQTT, beide mit gepinnten Images. Er ist allgemein gehalten: Gateway-ID, Broker-Adresse und Zugangsdaten stehen ausschließlich in `secrets/` auf dem Gateway, nie im Repository. Auf dem Pi liegt der Ordner unter `/srv/smart-gateway`.

| Datei                     | Zweck                                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `compose.yaml`            | Mosquitto 2.1.2 und Zigbee2MQTT 2.14.2, Speicherlimits, Log-Rotation                                                                           |
| `mosquitto.conf.template` | Mosquitto-Konfiguration nach ADR-0020 mit den Platzhaltern `{{GATEWAY_ID}}`, `{{BROKER_HOST}}`, `{{BROKER_PORT}}`                              |
| `render.sh`               | prüft `secrets/gateway.env`, füllt die Vorlage, schreibt `run/mosquitto.conf` (Modus 600, atomar)                                              |
| `mosquitto-entrypoint.sh` | kopiert die Geheimnisse beim Start für den Mosquitto-Benutzer lesbar in ein tmpfs und erzeugt die lokale ACL                                   |
| `test/gateway-test.sh`    | Docker-Test des Pakets (`bash gateway/test/gateway-test.sh`, braucht Docker und OpenSSL 3)                                                     |
| `deploy.sh`               | `SMART_PI=<user@pi-host> pnpm gateway:deploy [--migrate \| --fresh]`: installiert/aktualisiert den Stack auf dem Pi vom Mac                    |
| `migrate.sh`              | Pi-Teil des Umzugs (`--migrate`): Sicherung, Stopp, Restart-Policy, Kopie, Start, Rückweg; abgekoppelt auf dem Pi, Stand in `migration/status` |
| `start.sh`                | Start des Stacks auf dem Pi und Warten auf Z2M (online, stabil, Mosquitto healthy); von `deploy.sh` und `migrate.sh` genutzt                   |
| `test/deploy-tests.sh`    | Test von `deploy.sh` mit Stub-ssh/-rsync/-docker in einer Sandbox (`bash gateway/test/deploy-tests.sh`)                                        |
| `backup/`, `systemd/`     | nächtliches restic-Backup nach B2, wöchentlicher Restore-Test, systemd-Timer (Abschnitt „Backups“)                                             |
| `test/backup-tests.sh`    | Docker-Test der Backups mit lokalem restic-Repository und Stub-curl (`bash gateway/test/backup-tests.sh`)                                      |

## Dateien in `secrets/` (root `700`, Dateien `600`)

| Datei                                  | Inhalt                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gateway.env`                          | `GATEWAY_ID` (`gw-[a-z0-9]{8}`), `BROKER_HOST`, `BROKER_PORT`, `Z2M_SERIAL_DEVICE` (Pfad des Adapters auf dem Host)                                                                                                                                                                                                                         |
| `z2m.env`                              | `ZIGBEE2MQTT_CONFIG_MQTT_USER`, `ZIGBEE2MQTT_CONFIG_MQTT_PASSWORD`, `ZIGBEE2MQTT_CONFIG_FRONTEND_AUTH_TOKEN`                                                                                                                                                                                                                                |
| `passwd`                               | Passwortdatei des lokalen Brokers (Benutzer wie in `z2m.env`, erzeugt mit `mosquitto_passwd`)                                                                                                                                                                                                                                               |
| `ca.crt`, `gateway.crt`, `gateway.key` | CA und Gateway-Zertifikat für die mTLS-Bridge                                                                                                                                                                                                                                                                                               |
| `backup.env`                           | `B2_ENDPOINT` (Host ohne `https://`), `B2_BUCKET`, `B2_KEY_ID`, `B2_APP_KEY`, `RESTIC_PASSWORD`, `HC_BACKUP_URL`, optional `HC_RESTORE_URL` (Ping des wöchentlichen Wiederherstellungstests; `provision-gateway.sh` fragt sie nicht ab, von Hand ergänzen, `--force` behält die Zeile) (für das Backup des Pi, Schlüssel `smart-pi-restic`) |

`infra/deploy/provision-gateway.sh` (`SMART_PI=<user@pi-host> infra/deploy/provision-gateway.sh <gateway-id> [--force]`, läuft auf dem Mac im Heimnetz) schreibt alle diese Dateien in einer SSH-Sitzung als `sudo -n` (der Betreiber-Benutzer braucht passwortloses `sudo` und Docker; die Passwortdatei hasht das gepinnte Mosquitto-Image mit `mosquitto_passwd -U`, das Passwort steht nie in einer Kommandozeile). Zertifikat und Schlüssel kommen aus `~/.smart-pki` (`pki.sh issue-gateway`). Z2M-Passwort und Frontend-Token werden erzeugt und nicht ausgegeben (`sudo cat /srv/smart-gateway/secrets/z2m.env`); `--force` behält sie.

Die `.env`-Dateien sind einfache `KEY=Wert`-Zeilen: keine Anführungszeichen, kein `$` im Wert (Compose liest sie mit Interpolation). `render.sh` liest `gateway.env` nur zeilenweise und führt nichts davon aus; es läuft als root.

## Ablauf

`deploy.sh` ist der normale Weg, vom Mac aus (Runbook `docs/runbooks/gateway.md`, Abschnitt 11). Nur es prüft vor dem Start, dass kein zweites Zigbee2MQTT läuft (Adapter und Bridge-Zertifikat vertragen nur eins), dass der Datenordner nicht leer ist und kein unfertiges `zigbee2mqtt-data.partial` danebenliegt, setzt die Rechte und wartet, bis Z2M wirklich online ist. Ein Start von Hand mit `render.sh` und `compose up -d` überspringt das alles und ist nur auf einem **bereits umgezogenen** Pi gedacht (Daten vorhanden, kein altes Z2M läuft). Dann gehört `up -d --force-recreate mosquitto` dazu, weil `render.sh` die Datei ersetzt und die Einzeldatei-Einbindung sonst auf die alte zeigt:

```sh
sudo ./render.sh                                                           # schreibt run/mosquitto.conf, bricht bei ungültigen Werten ab
sudo docker compose --env-file secrets/gateway.env up -d --force-recreate mosquitto
sudo docker compose --env-file secrets/gateway.env up -d                   # dann Zigbee2MQTT
```

`SMART_GATEWAY_DIR` verlegt das Verzeichnis (Standard `/srv/smart-gateway`), nur für Tests.

## Backups

`deploy.sh` installiert zwei systemd-Timer (aus `systemd/`, mit dem tatsächlichen Ordner eingesetzt) und aktiviert sie:

- `smart-gateway-backup.timer`: täglich 03:30 (Ortszeit des Pi, `Persistent=true`) → `backup/backup.sh`. Es prüft `secrets/backup.env` (`KEY=Wert`-Zeilen, nie per `source` gelesen; Fehler nennen Zeile oder Schlüssel, nie einen Wert), sendet den healthchecks.io-Ping `/start`, führt im Compose-Dienst `backup` (Profil `backup`, `restic/restic` gepinnt, `backup/restic-job.sh`) `restic backup` von `zigbee2mqtt-data/` (ohne `log/`) und `secrets/` aus, danach `restic forget --prune` (7 täglich, 4 wöchentlich, 6 monatlich) und `restic check`, und pingt Erfolg oder `/fail`. Repository: `s3:https://<B2_ENDPOINT>/<B2_BUCKET>/pi`, Host-Tag ist die Gateway-ID.
- `smart-gateway-restore-test.timer`: sonntags 05:00 → `backup/restore-test.sh` stellt den letzten Snapshot der Z2M-Daten in ein Temp-Verzeichnis im Container wieder her und prüft `configuration.yaml` und `database.db` (vorhanden, nicht leer). Pingt `HC_RESTORE_URL`, falls in `backup.env` gesetzt (optional, von Hand ergänzt; `provision-gateway.sh` fragt sie nicht ab, behält sie aber bei `--force`); ohne sie meldet nur ein Fehler sich über `HC_BACKUP_URL/fail`.

**Uhr:** Der Pi hat keine Echtzeituhr; kurz nach dem Start kann die Zeit weit danebenliegen, und S3-Anfragen mit falscher Zeit scheitern. `After=time-sync.target` in den Diensten ordnet nur die Reihenfolge (das Target ist sofort erreicht, solange `systemd-time-wait-sync` nicht aktiviert ist). Deshalb warten `backup.sh` und `restore-test.sh` selbst, vor jeder restic- oder S3-Arbeit, bis zu 10 Minuten (`SMART_CLOCK_WAIT_SECONDS`), dass `timedatectl show -p NTPSynchronized --value` `yes` meldet. Sonst enden sie mit „clock not synchronized“ und Exit 1, und der `/fail`-Ping geht hinaus. Ohne `timedatectl` laufen sie sofort weiter. `TimeoutStartSec` der Dienste enthält die Wartezeit.

**Sicherung der laufenden Daten:** Das Backup liest `zigbee2mqtt-data/` im Betrieb. Gemessen am Quelltext von Zigbee2MQTT 2.14.2 (zigbee-herdsman 10.10.0): `database.db` und `coordinator_backup.json` schreibt herdsman in eine `.tmp`-Datei (mit `fsync`) und benennt sie dann per `rename` um; restic öffnet die Datei einmal und liest damit genau einen Stand (den alten oder den neuen), nie eine halbe Datei. `state.json` und `configuration.yaml` dagegen schreibt Z2M mit einfachem `writeFileSync` (in place, nicht atomar): eine Kopie genau im Moment des Schreibens kann abgeschnitten sein. Das ist hinnehmbar, weil Z2M eine beschädigte `state.json` beim Start ignoriert und neu aufbaut (nur der zwischengespeicherte Gerätestatus geht verloren) und `configuration.yaml` nur bei einer Einstellungsänderung oder beim Start geschrieben wird (selten, nachts um 03:30 so gut wie nie). Der Wiederherstellungstest prüft zusätzlich, dass jede Zeile der wiederhergestellten `database.db` mit `{` beginnt; **eine abgeschnittene `state.json` oder `configuration.yaml` kann er nicht erkennen** (er sieht sie nur als vorhanden und nicht leer). Dieses Restrisiko hinzunehmen ist eine Entscheidung des Betreibers. Ein liegengebliebenes `database.db.tmp` kann im Snapshot stehen und ist unschädlich.

Die Ping-URLs gehen per `curl -K -` über stdin (nie in einer Kommandozeile, nie im Log); die Geheimnisse erreichen den Container nur als Umgebung aus `backup.env`. Von Hand: `sudo bash /srv/smart-gateway/backup/backup.sh`, Log: `journalctl -u smart-gateway-backup`.

## Entscheidungen und Befunde (gemessen mit den gepinnten Images)

- **Geheimnisse und Rechte:** Mosquitto liest Passwortdatei und Bridge-Schlüssel erst nach dem Wechsel auf den Benutzer `mosquitto` (UID 1883); eine root-eigene Datei mit Modus 600 scheitert mit `Unable to open pwfile`. `mosquitto-entrypoint.sh` kopiert die vier Dateien deshalb aus `secrets/` (nur lesend eingebunden) in ein tmpfs, das dem Benutzer gehört. Auf der SD-Karte bleiben sie root-eigen mit 600. `run/mosquitto.conf` liest Mosquitto noch als root. **Healthcheck ohne Geheimnis:** der Entrypoint fügt der Passwortkopie im tmpfs den Benutzer `health` mit öffentlichem Passwort hinzu und schreibt eine ACL: alle Benutzer der `passwd` (Zigbee2MQTT) dürfen alles, `health` nur `$SYS/broker/uptime`, den lokalen Bridge-Status (`gw/+/bridge/connection`, `1`/`0`; Mosquitto veröffentlicht die Benachrichtigung bei gesetztem `notification_topic` auch lokal, nicht unter `$SYS`) und `zigbee2mqtt/bridge/state` lesen (Letzteres wartet `deploy.sh` ab, ohne ein Passwort in der Kommandozeile). So steht kein Geheimnis in `docker inspect` oder `ps`. **`render.sh` bricht ab**, wenn `z2m.env` fehlt oder `ZIGBEE2MQTT_CONFIG_FRONTEND_AUTH_TOKEN` leer ist (das Frontend wäre sonst offen). **Nach jedem `render.sh` Mosquitto neu erzeugen** (`docker compose --env-file secrets/gateway.env up -d --force-recreate mosquitto`): `render.sh` ersetzt die Datei (neuer Inode), die Einzeldatei-Einbindung zeigt sonst weiter auf die alte.
- **Umzug und alter Stack:** `migrate.sh` stoppt den alten Stack mit `compose stop` und behält ihn für den Rückweg. Ein von Hand gestoppter Container mit `restart: always` läuft nach einem Neustart des Docker-Daemons (also auch des Pi) wieder an, und dann hielten zwei Zigbee2MQTT den einen Adapter; mit `unless-stopped` bleibt er gestoppt (so steht es auf dem echten Pi), aber darauf verlassen sich die Skripte nicht. Deshalb speichert `migrate.sh`, sobald der alte Stack nachweislich steht, die Restart-Policy jedes alten Containers in `migration/old-restart-<Zeit>` (root, `600`, Zeilen `<Container> <Policy>`) und setzt sie mit `docker update --restart=no` auf `no`; scheitert das, wird zurückgerollt. Der Rückweg (automatisch wie von Hand) stellt die gespeicherte Policy vor dem Start des alten Stacks wieder her. Die Kopie der Daten entsteht in `zigbee2mqtt-data.partial` und wird erst danach per `mv` an den Platz gelegt: nach einem Stromausfall oder `SIGKILL` bleibt höchstens ein `.partial` liegen, und jedes Deploy (auch `--fresh`, `--migrate`) verweigert dann den Start. Direkt vor dem Start des neuen Stacks läuft dieselbe Prüfung auf ein fremdes Zigbee2MQTT wie im normalen Deploy.
- **Zeitzone:** Zigbee2MQTT läuft mit `TZ=Europe/Berlin`; `TZ` in der Umgebung von `docker compose` (oder in `secrets/gateway.env`) überschreibt das (`TZ: ${TZ:-Europe/Berlin}`).
- **Netz:** `gateway` ist ein gewöhnliches Bridge-Netz und kein `internal: true`: die Bridge braucht den Weg ins Internet, und Docker veröffentlicht keine Ports aus internen Netzen. Mosquitto veröffentlicht keinen Port; nur das Z2M-Frontend (8080, im Heimnetz, mit `auth_token`) ist erreichbar.
- **Z2M-Einstellungen per Umgebung:** Die Variablen heißen `ZIGBEE2MQTT_CONFIG_<PFAD>` (Großbuchstaben, `_` statt `.`), z. B. `…_MQTT_SERVER`, `…_MQTT_USER`, `…_MQTT_PASSWORD`, `…_FRONTEND_AUTH_TOKEN`, `…_ADVANCED_LAST_SEEN`, `…_AVAILABILITY_ENABLED`, `…_SERIAL_PORT`. Z2M 2.x hat das Frontend standardmäßig **aus**; deshalb setzt `compose.yaml` zusätzlich `…_FRONTEND_ENABLED=true` und `…_FRONTEND_PORT=8080`. Den Adapter reicht Compose immer als `/dev/zigbee` durch und setzt `…_SERIAL_PORT=/dev/zigbee`, so hängt der Start nicht davon ab, wie das alte Setup den Pfad genannt hat.
- **Z2M schreibt die Werte in die `configuration.yaml`:** Z2M 2.14.2 wendet die Variablen bei jedem Start an **und schreibt das Ergebnis zurück** (`onboard()` ruft `settings.write()`). Passwort und Token stehen danach im Klartext in `zigbee2mqtt-data/configuration.yaml`, Kommentare der Datei gehen verloren, Geräte, Namen, Kanal und Schlüssel bleiben unverändert (der Test prüft das), ein zweiter Start mit denselben Werten ändert die Datei nicht mehr (Prüfsumme). Folgen: Der Ordner `zigbee2mqtt-data` ist nur für root lesbar zu halten (Modus 700, `configuration.yaml` 600), und beim Umzug wird der Datenordner kopiert, nie die Datei des alten Stacks verändert.

## Was der Test beweist (und was nicht)

`test/gateway-test.sh` startet das Paket wirklich (`compose.yaml` mit den gepinnten Images), verbunden über mTLS mit einem Wegwerf-Broker (Image aus `infra/broker`, Wegwerf-CA aus `infra/pki/pki.sh`). Geprüft werden: `render.sh` (ungültige ID, Host, Port: keine Datei geschrieben, alte Datei unberührt; gültiger Lauf: Modus 600, nur die Platzhalterzeilen weichen von der Vorlage ab), die Werte nach ADR-0020, root-eigene Geheimnisse mit Modus 600 (mit Gegenprobe ohne Kopie), Healthcheck ohne Geheimnis und ACL (`health` liest nur drei Topics: `$SYS/broker/uptime`, den lokalen Bridge-Status `gw/+/bridge/connection` und `zigbee2mqtt/bridge/state`; Z2M-Benutzer frei), Bridge online (`gw/<id>/bridge/connection` retained `1`), `zigbee2mqtt/x` kommt als `gw/<id>/z2m/x` an, ein Befehl `gw/<id>/z2m/x/set` kommt lokal genau einmal an, 20 QoS-1-Nachrichten während eines Ausfalls des Plattform-Brokers kommen nach dessen Neustart in Reihenfolge und ohne Duplikate an; dasselbe mit 20 QoS-0-Nachrichten (Z2M publiziert QoS 0) bei gekappter Netzverbindung, nachdem die Bridge den Ausfall bemerkt hat.

Für Zigbee2MQTT gibt es ohne Adapter eine Grenze: Z2M liest und wendet die Einstellungen an, startet `zigbee-herdsman`, scheitert am Öffnen der seriellen Schnittstelle (`/dev/null` steht stellvertretend) und beendet sich. Bewiesen sind damit die Variablennamen (sie landen in den richtigen Schlüsseln), dass die Einstellungen gültig sind, dass Geräte und Namen erhalten bleiben und dass ein erneuter Start die Datei nicht mehr ändert. **Nicht** bewiesen sind der Verbindungsaufbau von Z2M zu Mosquitto (das passiert erst nach dem Adapter), das Frontend und die Zigbee-Funktion; sie prüft die Inbetriebnahme am echten Pi (Runbook). Die Anmeldung mit den Z2M-Zugangsdaten am lokalen Broker prüft der Test mit demselben Benutzer und Passwort über `mosquitto_pub`.
